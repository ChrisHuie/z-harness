[[reference_review_patterns]] catalogs the patterns reviews *flag*. This is the complement: a reviewer's proposed *fixes* can be **factually wrong** because the premise doesn't hold against the current code. Blindly applying a reviewer's literal fix can REGRESS behavior. Verify each fix against the code (read the dispatch path, the class default, the function body) before applying; when a fix is wrong, do the change that achieves the reviewer's *underlying goal* and surface the deviation with evidence (file:line) in the PR reply.

**Why — 4 instances in PR #1307 (all verified wrong against code):**
1. **A2**: "raise `AdCPAdapterError` so the boundary handler funnels it through `_build_error_envelope`." FALSE — the 4 push-notif sites are JSON-RPC RPC methods dispatched by the a2a-sdk `JsonRpcDispatcher`, which `except A2AError → structured` but `except Exception → InternalError(str(e))` (flattened). `InternalError` IS an `A2AError`; `AdCPAdapterError` is NOT. So the literal fix produces NO envelope (strictly worse). Fix that met the goal: `InternalError(..., data=build_two_layer_error_envelope(...))` — envelope rides in `error.data`.
2. **A1**: "the 3 `error_code="INVALID_REQUEST"` kwargs are redundant (already the class default) — drop them." FALSE — `AdCPValidationError._default_error_code` is `VALIDATION_ERROR`, so dropping changed the wire code; integration wire-tests (which deliberately pin INVALID_REQUEST) caught it (unit didn't). Fix: typed `AdCPInvalidRequestError(AdCPValidationError)`.
3. **T7**: "pin to `pytest.raises(ValidationError)` — fires at the Pydantic layer." FALSE for this test — `create_media_buy_raw` catches the Pydantic `ValidationError` and converts to `AdCPValidationError` (so the literal fix would fail). The valid core point (don't assert the version-fragile Pydantic string) still applied.
4. **T5**: "wrap `TenantFactory.create_sync(...)`." FALSE — `create_sync` does not exist anywhere in the repo; and the factory-boy factories use `SubFactory`/`RelatedFactory` that conflict with the explicit-FK-string test helpers.

**The false premise can be about the SPEC or the TEST-ENV TAXONOMY, not just the code.** A reviewer flagging "behavior X is a defect — change it" can be wrong because X is *mandated/intended* by an authority they didn't consult. Two recurring authorities to check before changing behavior:
5. **BDD feature spec** — a `.feature` file may MANDATE the flagged behavior, even when the whole use-case is xfail-managed (unimplemented). E.g. a reviewer says "this list endpoint's empty-list+`errors[]` advisory should `raise`"; the `BR-UC-*` spec explicitly mandates the *advisory* (only the no-auth case raises) and the relevant scenarios are xfail with aspirational non-standard codes. Migrating to a raise would VIOLATE the spec and break the `then_empty_with_error`-style step (which asserts a non-None success response with `errors[]`). Check: grep the feature file + the `@then` step body; run the scenarios to see pass/xfail.
6. **Unit-vs-integration env taxonomy** — a reviewer says "Env A only exposes `call_impl`, asymmetric vs Env B's `call_a2a`/`call_mcp`." But the multi-transport coverage often lives in a separate *integration* env (a `*DualEnv`/`*Env` wired into BDD `conftest`, parametrized across transports), while the flagged env is the intended *unit* variant (the documented `*EnvUnit` split). Adding multi-transport to a fully-mocked unit env duplicates the integration env at lower fidelity. Check: grep for a sibling `Dual`/integration env that dispatches the same `_impl`/`_raw`, and the `tests/CLAUDE.md` env table.

Also: a review run against an older commit (its base SHA is usually stated in the comment) can flag sites already migrated in later commits — verify each cited file:line against CURRENT code; "stale line ref" is common.

**7. This applies to items INHERITED from a colleague's review, and that is where we actually failed.** On a re-review you carry a ledger of outstanding items, some raised by other reviewers. Verify each one's premise before listing it as outstanding — we had been applying this rule only to our *own* proposals, and deference is not verification. Instance: a colleague's item asked that deny/allow assertions be re-expressed through the harness's `assert_wire_error`/`wire_field`. That path emits a transport-native JSON-RPC error, `issubclass(TaskNotFoundError, AdCPError)` is `False`, so `tests/harness/dispatchers.py` never populates `wire_error_envelope` and the helper asserts its own absence — the ask was **unsatisfiable**, and we carried it into a re-review ledger for a full round before a specialist falsified it. Cost of not checking: you send the author to do impossible work, and it spends the credibility you need for the items that are real. Charter §1.7b.

**How to apply:**
1. For every reviewer fix that changes a wire code, exception type, or dispatch path, trace it: read the SDK/boundary code, confirm the class default (`_default_error_code`), check what the wrapper actually does (converts vs propagates), grep that the named API exists. Unit tests often miss wire-code regressions — the integration/wire-envelope tests are the authority ([[wire_envelope_policy]]). For behavior-change fixes, ALSO check the BDD spec + env taxonomy (above) before acting.
2. When the literal fix is wrong, implement the change that achieves the reviewer's *intent*, and for wire-contract or reviewer-contradiction forks, surface it to the user with evidence before committing (this PR: A2 + INVALID_REQUEST were AskUserQuestion decisions; both picked the corrected option).
3. Record every correction (with file:line evidence) so it goes into the PR reply — the reviewer needs the rationale to accept the deviation. Ties [[feedback_verify_before_asserting]], [[feedback_truth_over_optimism]], [[feedback_detecting_subagent_overconfidence]].
