Do NOT put durations, time estimates, or timeframes on deliverables or work — no "two weeks", "months", "quarters", "days-to-weeks", "9–18-month moat", "how long X takes". User (2026-07-11): "you don't understand time. Don't reference it."

**Why:** I don't have the context to estimate time and get it wrong; it reads as presumptuous noise. The USER sets the timeline (e.g. they said they'll rebuild the whole sales agent in 2 weeks — their call, stated by them, not my estimate).

**How to apply:** talk about SCOPE, sequence, and what-gets-built — never duration. Kill "two-week demo"-style labels on deliverables. Hard external dates that are real dependencies (protocol version deadlines, court rulings) are facts, not my estimates — those can stand, but don't editorialize timing around them. Whenever tempted to say "how long," state scope instead. Applies to my responses AND to repo/strategy docs I author.

**Stronger form (user, 2026-07-11):** "how long it takes me to build has no relevance to you. Your job is to efficiently plan a full implementation regardless of time even… it is an agentic problem and I can do it as slow or fast as I want depending on how I want to spend." ⇒ Plan the FULL implementation, complete, on scope/architecture/correctness merits. Sequence by **dependency + risk** (what enables/de-risks what), NEVER by speed or time-to-ship. Duration is meaningless for an agentic build (the user allocates effort). Do NOT frame any deliverable as "quick / thin / demo / first flex" to save time — the deliverable is the full, correct thing; ordering is about dependencies, not haste.
