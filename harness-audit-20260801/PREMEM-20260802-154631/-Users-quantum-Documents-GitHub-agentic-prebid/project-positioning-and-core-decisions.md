Strategic decisions locked in the 2026-07-10/11 architecture session — now written + reconciled into the repo docs (`docs/{POSITION,ARCHITECTURE,BUILD-PLAN,STATE,EXECUTION,PARITY,SUBSTRATE}.md` + `docs/design/` briefs incl. `durable-execution.md`; reconciled 2026-07-11, scratchpad `docs-reconciliation.md`):

**Core language — LOCKED: Python core + generated TS/Go bindings.** The "GAM lives in Python" argument weakened when SalesAgent rewrote GAM to TypeScript, but user still chose Python: single source of truth, DBOS-native durability, pydantic gives model + JSON-schema free. TS-GAM becomes a binding/adapter-layer detail, not a reason to move the core.

**Durable-execution engine — LOCKED: DBOS, explicitly NOT Temporal.** DBOS = a library over our OWN Postgres → workflow-step + business write in ONE txn (exactly-once outbox), workflow state is queryable SQL (= the modular-UI read model for free), `pip install` + a Postgres adopters already run (embeddable/low-ops = serves "serve anyone"). Temporal = a separate cluster with its own history store → reintroduces a two-store boundary, locks state inside the cluster (UI needs a separate projection), adds ops back (fights serve-anyone); its maturity/scale/polyglot edge answers a scale question we don't have (our workflows are ad-booking sagas, not millions of concurrent workflows). De-risk = own-the-seam: durable execution is an OWNED primitive ([[project-neutral-primitives-charter]] T2) behind a thin Commitment/durable-exec interface → DBOS is the impl, Temporal a possible future backing ADAPTER not a rewrite; R0 (crash/resume spike) proves DBOS is solid enough. Replaces the TS SalesAgent's BullMQ-on-Redis core (scratchpad/execution-substrate.md).

**DBOS due-diligence (2026-07-11, research-grounded):** maintainer = DBOS, Inc. (Stonebraker co-founder/architect; Qian Li CEO, Peter Kraft CTO; Zaharia = "founding advisor"). DBOS Transact = MIT, Python-first (also TS/Go/Java), v2.26, active; self-reported adopters BMS/Yutori/Dosu. Company-risk = seed-only ($8.5M Mar-2024, no later round found) + a reverted outside-CEO + an OS→library pivot = a YELLOW flag, but MITIGATED by the design: MIT license + durable state as ordinary tables in YOUR Postgres (runs on any PG — RDS/Supabase/Neon — no extension) ⇒ company failure loses future dev, NOT your running system or data. Evaluated + REJECTED "pg-durable" = `microsoft/pg_durable` (open-sourced Jun-2026): a Rust PG-EXTENSION, SQL-DSL-only, NO Python, PG17-only, PREVIEW ("do not use in production"), Azure-HorizonDB-steered — poor fit; DBOS is closer to the "simple durability on your Postgres" idea than pg_durable is. Re-check pg_durable only if it grows a Python client + leaves preview. CONFIRMS the risk-register #17: "swap DBOS→Temporal behind a thin seam" is SEMANTICALLY ILLUSORY — same-txn-exactly-once + SQL-queryable-state are Postgres-native properties Temporal's separate-cluster model can't reproduce; the seam ports the interface, not the guarantees. Real escape hatch = other Postgres-co-located engines (pg_durable/Hatchet-with-caveats), NOT Temporal. Correction: Hatchet ≠ DBOS on the same-txn axis (separate server owns its own PG → business write + checkpoint in different transactions). DBOS is the ONLY surveyed option that is simultaneously embeddable-Python-library + your-own-Postgres-as-plain-tables + documented same-transaction exactly-once.

**Agent-intelligence layer — LOCKED: model-agnostic; pydantic-ai behind a `core/models/` seam; NO litellm/CrewAI.** Verified in the two references: the AdCP SalesAgent is already model-agnostic (a 6-provider catalog + thin hand-rolled client descended from pydantic-ai, doing 4 narrow decision tasks — but parse-and-hope, no schema validation); AAMP's seller-agent is CrewAI+litellm (a heavy framework we reject). Choosing thin-owned = DBOS-not-Temporal one layer down. Approach = N-faces at the model layer: a `decide(task, ctx) -> pydantic-validated output` port; pydantic-ai is the default impl, swappable, guard `test_model_independence`. Two bright lines: (1) usage may grow but IMPORT SITES may not — everything routes through the one seam, so it stays deletable; (2) the model lives ONLY in the decision layer (judge/extract/rank/negotiate), NEVER in mechanism (translation/booking/idempotency/receipts stay deterministic), every call wrapped as a DBOS step (non-determinism quarantine). Chosen for speed; schema validation itself comes from plain pydantic (already core), so the seam lets us hand-roll later with no rewrite. Detail: scratchpad `model-layer.md`; future `docs/design/model-agnostic-agent.md`.

**Positioning model — LOCKED: "Prebid.js for the agentic era."** A Prebid-governed NEUTRAL SUBSTRATE that is Prebid-owned and vendor/protocol-neutral at once — owning the neutral layer everyone stands on is the sovereignty play, not a contradiction. Five sub-calls:
1. **Rebuild, not refactor** — greenfield the role-symmetric neutral core; harvest the existing prebid/salesagent for PARTS only (GAM adapter, mock ad server, testing hooks) behind a clean boundary. Owes the Sales Agent team a "substrate you'll want to stand on" story, not "we rebuilt your thing."
2. **Serve anyone** — IAB, Scope3/AAO, independents all welcome to build on it. Breadth = sovereignty (if their agents run on our substrate, no one controls Prebid). Obliges an Apache-2.0-class permissive license + visibly neutral governance.
3. **Both / all** — build a substrate library AND reference agents; not ideological about lib-vs-product; build order is whatever proves the position fastest.
4. **Governance is three stacked layers:** substrate (our code/core/roadmap) = **Prebid** (LOCKED, the sovereignty anchor); the protocols we bridge = **stay with their owners** — IAB Tech Lab (AAMP/ARTF), AAO/Scope3 (AdCP) — we conform + prove it with a conformance suite, we don't own them (LOCKED, healthy); the **trust root** (identity, mandates, signed authority, settlement) = **OPEN, likely multi-party / standards-anchored** because a trust root one org controls isn't neutral — rides with the deferred settlement rail.
5. **Sequencing = RESOLVED into a 4-phase roadmap** (synthesized from 4 research streams). Logic: lead with the bridge (contested, ~2–3-quarter window, consolidation is the real risk), prove it via durability (quieter 9–18-mo moat), lock neutrality early via Prebid.org. Serial spine R0→R1→R2→R5→R7. Phases: P1 (now→late Jul) R0 DBOS spike + R1 2-wk saga demo, v3.x-only + build-to-AdCP-idempotency (ALREADY required since 3.1.0 in the v3 line; 3.2/Grader only tighten enforcement, Aug-1 v2 EOL removes the fail-open escape), emit a measurable number; P2 (Aug) R2 role-symmetric core + harden + court both-camp buy-in; P3 (Sep) R3 AdCP face ∥ R4 AAMP face → R5 bridge, aim demo at Programmatic I/O NY Sep 28–29 / AdWeek Oct 5–8; P4 (Q4→2027) R6 reference agents + R7 default posture, hosted/rail LAST. Hard pins: AdCP v2 EOL Aug 1 (v3-only); AAMP 2.0 (~Apr 2026) is the stable target; don't design into HMAC (AdCP 4.0 ~2027). Full roadmap in coverage-map.html §07 + scratchpad/sequencing-research.md.

**Why:** all of this serves the substrate-ownership thesis in [[project-substrate-ownership-strategy]] — own the neutral layer so no protocol/org controls Prebid. Prebid.js is the proof the "neutral + owned" combination works.

**How to apply:** build in Python; don't retrofit salesagent (see [[reference-salesagent-python-in-legacy]]); assume Apache-2.0-class license; treat protocol specs as owned-elsewhere (conform, don't fork); keep the trust-root governance question explicitly open. First proof (<2 weeks) = crash-safe saga-commit across AdCP (1 atomic call) ↔ AAMP/OpenDirect (N non-atomic line ops) that refuses to silently drop unmappable fields (allow_lossy=False), DBOS in buyer/core, exactly-one asserted at the mock ad server, one durable approval gate. Consolidated map artifact: coverage-map.html.
