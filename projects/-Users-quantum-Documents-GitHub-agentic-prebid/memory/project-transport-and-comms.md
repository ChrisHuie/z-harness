Resolves the TECHNICAL half of red-team issue-3 (the A2A/MCP communication + capabilities model + how it wires into our design) — user caught the strategic-only resolution as a gloss. Verified vs primary specs.

**VERSION ANCHORS (bind to these):** A2A **v1.0.0** (LF-governed, stable; secondary "v1.2" blog claims unverified). MCP **2025-11-25** (current published; introduced the Tasks primitive) — BUT a **2026-07-28 RC removes the `initialize` handshake + sessions → STATELESS core**, makes Tasks an opt-in extension, drops `tasks/list`. Build against 2025-11-25; DESIGN FOR MCP GOING STATELESS (never depend on MCP sessions/handshake).

**DIVISION OF LABOR (official, confirmed): A2A on the OUTSIDE edge (agent-to-agent = the deal); MCP on the INSIDE (agent-to-tool). One agent is BOTH an A2A server (exposes skills) AND an MCP client (drives tools).** Our seller agent = A2A server exposing a negotiate/transact SKILL; buyer = A2A client. Deal negotiation = an A2A **Task**: rounds = messages sharing one **`contextId`**; offers/bids = **`DataPart`** (arbitrary structured JSON); hold-between-rounds = **`input-required`** (non-terminal, resumable); long gaps (mins/hrs/days) = **push notifications** (secured webhook — JWS/JWT verified + replay-protected — then `tasks/get` pull). Commit = terminal state + **Artifact**. Tool/signal access (inventory, floor-price, bid-signals, identity/audience, forecasting, brand-safety) = **MCP tools** the seller calls as an MCP client.

**THE KEY FINDING — A2A/MCP give the choreography but PUNT the two hardest deal guarantees, which are EXACTLY our owned primitives:** (1) a **durable HOLD on terms** (escrow/lock-with-expiry) — NOT a primitive in either (MCP Tasks `ttl` = retention/expiry, not a terms-lock); (2) **crash-resumable durable state** — A2A spec: "no guidance on task state persistence," no missed-event-replay; MCP RC goes stateless. So durable/crash-resumable negotiation state is squarely OURS. Substrate-ownership opening the charter predicted: **A2A = the conversation; our DBOS-backed order-of-record = the durable truth A2A doesn't provide → we COMPLETE A2A's mechanism layer, not compete.** "Model proposes (A2A messages) → mechanism disposes (our durable Gate/Commit)" maps perfectly. [[project-order-of-record-pivot]] [[project-neutral-primitives-charter]]

**MANDATE rides ABOVE A2A, not in it → ours to shape.** A2A core = transport + signed Agent Cards (JWS over JCS-canonicalized) + standard auth (apiKey/http/oauth2/oidc/mutualTls). Delegated-authority MANDATES are an EXTENSION: **AP2 (Agent Payments Protocol, A2A extension, ~Apr-2026, GOOGLE-originated) = Intent/Cart/Payment mandates as W3C Verifiable Credentials (ECDSA-signed).** So the mandate is OURS to author or bind behind a mandate seam — same Google-anchoring caution as A2A itself (AP2 is Google-originated → bind the frozen VC core, keep plural, don't let AP2 go load-bearing). This is the A1 mandate work; the spec confirms the slot is open. [[project-agent-discovery-decapture]]

**CAPABILITIES:** A2A = DECLARATIVE, NO handshake — fetch the signed Agent Card: `capabilities` {streaming, pushNotifications, stateTransitionHistory, extensions} + `skills` {id/name/desc/tags/examples/inputModes/outputModes; SOFT selection — you route via payload/metadata, no hard skillId dispatch}. MCP = HARD-gated `initialize` handshake (both parties only use negotiated caps) — but the RC removes it. Bridge capability-declaration stays in our `AgentDescriptor` (A2A card ↔ AdCP `get_adcp_capabilities`).

**REST = a FIRST-CLASS A2A binding** (answers the REST question): A2A v1.0 defines THREE co-equal bindings — **JSON-RPC / gRPC / HTTP+JSON(REST)** — with equivalence guarantees, NONE mandatory (Agent Card `supportedInterfaces[]`; first = preferred; v1.0 removed the old `url`/`preferredTransport`). Plus MCP Streamable HTTP (stdio for local). So REST is both an A2A binding AND the LCD standalone/AAMP transport. Transport stays plural behind the seam; the seam MUST abstract PUSH-native (A2A SSE/webhook) vs POLL-native (REST/AAMP status).

**IMPEDANCE MISMATCHES (handle, not blockers):** A2A `input-required` is DIRECTIONAL (agent asks its driving client), NOT a symmetric peer volley → model negotiation as seller's-Task-soliciting-buyer, or linked tasks / state-in-payload (matches our "pen-in-opposite-hands" A2 finding). Sub-second latency isn't A2A's thing (fine — DEAL layer, not impression).

**CAVEATS:** MCP churning hard (2026-07-28 RC — handshake+sessions gone). A2A JSON-RPC method literal strings (`message/send`, `tasks/get`, `tasks/pushNotificationConfig/set`…) need byte-level confirmation vs the spec's JSON schema before hardcoding wire strings (research flagged residual uncertainty; `SendMessage`/`GetTask` are the abstract/gRPC names). AP2 field-level detail needs the raw AP2 spec if we build to it. Full spec detail: scratchpad tasks output, research 2026-07-11.
